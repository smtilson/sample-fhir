## A. Runtime & Configuration

### [AUDIT-CFG-01] Settings Default to Demo Mode with Known Seed Credentials
- **Severity:** High
- **Related Tickets:** `[SMP-EP1-TK05]`
- **Affected Files:** `sample_flutter_app/backend/src/core/config.py` (L22–23), `sample_flutter_app/backend/src/core/database.py` (L58–70, L122–123)
- **Finding:** `Settings.app_env` defaults to `"demo"` and `database_url` defaults to `"memory"`. Any deployment that forgets to set environment variables will silently start with an ephemeral in-memory database (all writes lost on restart) and seed accounts with the publicly known password `"password123"`. `app_env` is a free-form `str`, so typos (e.g. `APP_ENV=prod`) are accepted without error.
- **Recommendation:**
  1. Type `app_env` as `Literal["demo", "test", "development", "production"]`.
  2. Make the default fail-safe (e.g. `"development"` requiring an explicit `DATABASE_URL`), and opt into demo mode explicitly (`APP_ENV=demo`).
  3. Refuse to start (raise at startup) if `app_env == "production"` and `database_url == "memory"`.
- **Acceptance Criteria:**
  - Unit test: `Settings(app_env="prod")` raises `ValidationError`.
  - Unit test: production + memory configuration raises on `init_db()`.
  - README documents the demo launch command with `APP_ENV=demo`.
- **Devin re-Cognito:** In a Cognito-backed deployment there would be no seeded local passwords at all; seed users would be created in a separate non-production User Pool. Keeping demo credentials strictly opt-in mirrors that separation.

### [AUDIT-CFG-02] Ambiguous Memory / Demo / Seeding Activation Rules
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP1-TK05]`
- **Affected Files:** `sample_flutter_app/backend/src/core/database.py` (L107, L122)
- **Finding:** Memory mode activates when `database_url == "memory"` **or** `app_env == "demo"`. Therefore `APP_ENV=demo` with a real `DATABASE_URL` still uses memory, silently ignoring the URL. Seeding is keyed only on `app_env == "demo"`, so `DATABASE_URL=memory` with `APP_ENV=development` yields an empty in-memory DB. The combinations are not documented.
- **Recommendation:** Make the database backend depend solely on `database_url` and seeding depend solely on an explicit flag (e.g. `seed_demo_data: bool`, or `app_env == "demo"`). Document the matrix.
- **Acceptance Criteria:**
  - A documented table of `(APP_ENV, DATABASE_URL) → (backend, seeded?)`.
  - One atomic test per row of that table.

### [AUDIT-DB-01] Runtime Module Imports a Dev-Only Dependency
- **Severity:** High
- **Related Tickets:** `[SMP-EP1-TK05]`, `[ISSUE-DEP-03]`
- **Affected Files:** `sample_flutter_app/backend/src/core/database.py` (L17–18, L39–48), `sample_flutter_app/backend/pyproject.toml` (L53)
- **Finding:** `database.py` imports `mongomock.database` and `mongomock_motor` at module top level and applies the monkeypatch at import time. `mongomock-motor` is declared only under `[project.optional-dependencies].dev`. A production image installed without `[dev]` would fail with `ModuleNotFoundError` the moment `src.main` is imported — even though production never uses the mock. The monkeypatch also runs in every environment, including production.
- **Recommendation:**
  1. Move the mock client construction and the shim into a dedicated module (e.g. `src/core/mock_db.py` or `src/core/compat/mongomock_shim.py`).
  2. Import it lazily, only inside the memory branch of `init_db()`.
  3. Alternatively, promote `mongomock-motor` to a `demo` extra and document it.
- **Acceptance Criteria:**
  - In a venv with only base dependencies, `python -c "import src.main"` succeeds.
  - `mongomock` is not imported when `DATABASE_URL` is a real URI (assert `"mongomock" not in sys.modules` in a test).

### [AUDIT-DB-02] Duplicated mongomock Shim; Test Copy Wraps an Already-Patched Function
- **Severity:** Medium
- **Related Tickets:** `[ISSUE-DEP-03]`
- **Affected Files:** `sample_flutter_app/backend/tests/conftest.py` (L28, L32–51), `sample_flutter_app/backend/src/core/database.py` (L29–48)
- **Finding:** The shim exists in two places. `conftest.py` imports `src.main` at L28, which imports `src.core.database`, which applies the runtime patch. Only afterwards does `conftest.py` capture `_orig_list_collection_names` (L42) — so the "original" it captures is already the patched function, and the test copy merely double-wraps it. The test copy is therefore redundant today, and the two copies can drift silently.
- **Recommendation:** Keep exactly one shim in a single compat module (see `[AUDIT-DB-01]`), make it idempotent (guard against re-patching), and have both the demo path and `conftest.py` call the same `apply_mongomock_compat()` function.
- **Acceptance Criteria:**
  - Searching the repository for `_patched_list_collection_names` yields exactly one definition.
  - Calling `apply_mongomock_compat()` twice does not double-wrap (unit test).
  - `[ISSUE-DEP-03]` updated to reference the single location.

### [AUDIT-DB-03] No Client Shutdown, No Logging, Mixed Responsibilities in `init_db`
- **Severity:** Low
- **Related Tickets:** `[SMP-EP1-TK05]`
- **Affected Files:** `sample_flutter_app/backend/src/main.py` (L32–36), `sample_flutter_app/backend/src/core/database.py` (L26–27, L105–123)
- **Finding:** The lifespan yields without closing the Motor client on shutdown. There is no logging of which backend/database was selected (the existing `# TODO: Add logging` acknowledges this). `init_db()` combines client selection, compat patching, Beanie initialization, and seeding (also acknowledged by an existing TODO).
- **Recommendation:** Split into `build_client(settings)`, `init_odm(db)`, and `seed_demo_data()`; have `init_db()` return the client so the lifespan can `client.close()` after `yield`. Log the selected mode (never the full URL, which may contain credentials).
- **Acceptance Criteria:**
  - Lifespan closes the client on shutdown (test with a fake client).
  - Startup logs one line indicating `mode=memory|mongodb` and `seeded=true|false`, with no credentials.

### [AUDIT-APP-01] Inconsistent Import Strategy (`sys.path` Hack vs. pytest Config)
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP0-TK01]`, `[SMP-EP1-TK05]`
- **Affected Files:** `sample_flutter_app/backend/src/main.py` (L21–24), `sample_flutter_app/backend/pyproject.toml` (L66–78)
- **Finding:** `main.py` inserts the backend root into `sys.path` at import time. Meanwhile `pyproject.toml` sets `pythonpath = ["src"]` with a comment claiming this makes `from src.main import ...` work; that is inaccurate — putting `src/` on the path enables `import main`, not `import src.main`. `src.` imports in tests actually resolve because pytest inserts the rootdir (via `tests/__init__.py` package detection). Three mechanisms coexist, which is confusing and fragile.
- **Recommendation:** Pick one strategy:
  - **Option A:** Treat `src` as the package (current import style), set `pythonpath = ["."]`, run Uvicorn from `backend/` (or with `--app-dir`), and remove the `sys.path` hack.
  - **Option B:** Rename to a real package (e.g. `src/sample_todo/...`) and install with `pip install -e .`.
- **Acceptance Criteria:**
  - `sys.path` manipulation removed from `main.py`.
  - Both `pytest` and `uvicorn src.main:app` (documented command) work from `backend/`.
  - `pyproject.toml` comment accurately describes the mechanism.

### [AUDIT-APP-02] No CORS Middleware — Blocks Flutter Web
- **Severity:** High (blocks Epoch 2)
- **Related Tickets:** `[SMP-EP2-TK01]`, `[SMP-EP0-TK02]`
- **Affected Files:** `sample_flutter_app/backend/src/main.py` (L39–60)
- **Finding:** `create_app()` registers no `CORSMiddleware`. Flutter Web (the first rollout platform) runs on a different origin (e.g. `http://localhost:<random-port>`), so browsers will block every API request with a CORS error. This will be the first failure encountered in Epoch 2.
- **Recommendation:** Add `CORSMiddleware` with an allow-list driven by settings (`cors_origins: list[str]`), defaulting to localhost origins in demo/development and requiring explicit configuration in production. Avoid `allow_origins=["*"]` combined with credentials.
- **Acceptance Criteria:**
  - API test: an `OPTIONS` preflight from an allowed origin returns `access-control-allow-origin` matching that origin.
  - API test: a disallowed origin receives no allow header.

- **Acceptance Criteria:** In a clean venv, `pip install -e ".[dev]"` succeeds from `backend/`, and `python -c "from src.main import app"` succeeds from a directory *outside* `backend/`.

### [AUDIT-DEP-02] Dependency Declarations Drift from What Is Installed / Used
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP0-TK01]`, `[ISSUE-DEP-02]`
- **Affected Files:** `sample_flutter_app/backend/pyproject.toml` (L32–56), `requirements.txt` (L15–48)
- **Finding:**
  - `email-validator` (required by `EmailStr` in `src/schemas/user.py`) is declared in **neither** file; it was installed manually after an `ImportError`. Use `pydantic[email]` or list it explicitly.

## C. API Layer & Architecture

### [AUDIT-ARCH-01] No Service / Repository Layer; Routers Call Beanie Directly
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP1-TK03]`, `[SMP-EP1-TK04]`
- **Affected Files:** `sample_flutter_app/backend/src/api/users.py`, `sample_flutter_app/backend/src/api/tasks.py`; standard in `AGENTS.md` §3.2 and `sample_flutter_app/docs/02_DEVELOPMENT_PLAN.md` (L28, `services/`)
- **Finding:** Business rules (duplicate-email check, password hashing on update, user-existence check on task create) live inside route handlers alongside Beanie queries. `AGENTS.md` requires Clean/Hexagonal architecture with domain logic decoupled from database drivers and frameworks, and the development plan lists a `services/` folder that does not exist. This makes the rules untestable without HTTP and couples them to Beanie.
- **Recommendation:** Introduce `src/services/user_service.py` and `src/services/task_service.py` holding business rules, raising domain exceptions (e.g. `EmailAlreadyRegistered`, `UserNotFound`), which routers translate to HTTP. Repository abstraction can be deferred, but services should depend on a narrow interface. Split into one ticket per service to keep granularity.
- **Acceptance Criteria:**
  - Route handlers contain no direct `User.find_*` / `Task.find_*` calls.
  - Service-level unit tests cover each rule without an HTTP client.

### [AUDIT-API-01] Duplicated Get-or-404 and DTO Mapping Code
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP1-TK03]`, `[SMP-EP1-TK04]`
- **Affected Files:** `src/api/users.py` (L80–92, L108–120, L154–166, plus `UserOut(...)` at L52, L68, L94, L140), `src/api/tasks.py` (L100–112, L130–142, L171–183, plus `TaskOut(...)` at L58, L82, L114, L155)
- **Finding:** The same try/except + `None` check block is repeated seven times, and DTO construction is hand-written eight times. A field added to a model must be updated in four places per router.
- **Recommendation:**
  - A FastAPI dependency (e.g. `get_user_or_404`, `get_task_or_404`) injected via `Depends`.
  - A single mapper per entity (e.g. `UserOut.from_document(user)` converting `PydanticObjectId` to `str`).
- **Acceptance Criteria:** Each router contains one lookup helper and one mapper; existing API tests pass unchanged.

### [AUDIT-API-02] Broad `except Exception` Masks Real Failures
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP1-TK03]`, `[SMP-EP1-TK04]`
- **Affected Files:** `src/api/users.py` (L82, L110, L156), `src/api/tasks.py` (L38, L102, L132, L173)
- **Finding:** Every lookup catches `Exception`. The intent is to map malformed ObjectIds to 404 (or 400 for `user_id` in task creation), but database outages, timeouts, or programming errors are also converted to "not found", which hides incidents and misleads clients.
- **Recommendation:** Validate the ID explicitly (`bson.ObjectId.is_valid(id)` or a `PydanticObjectId` path parameter type), and catch only the specific validation exception. Let other errors surface as 500 and be logged.
- **Acceptance Criteria:** Test with a stubbed `User.get` raising a non-validation error asserts a 500 response, not 404.

### [AUDIT-API-03] Unhandled `DuplicateKeyError` Race Returns 500
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP1-TK03]`
- **Affected Files:** `src/api/users.py` (L37–50, L123–138)
- **Finding:** Create and update check for an existing email, then write. Two concurrent requests can both pass the check; the unique index then raises `pymongo.errors.DuplicateKeyError`, which is not caught and becomes HTTP 500. The unique index is the real guarantee; the pre-check is only a convenience.
- **Recommendation:** Wrap `insert()` / `save()` and map `DuplicateKeyError` to the same `400 "Email already registered"` (or adopt `409 Conflict` consistently — decide in the open questions below).
- **Acceptance Criteria:** API test that patches the pre-check away (or inserts directly before the call) asserts 400/409, not 500.

### [AUDIT-API-04] Deleting a User Orphans Their Tasks
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP1-TK03]`, `[SMP-EP1-TK04]`
- **Affected Files:** `src/api/users.py` (L147–168)
- **Finding:** `DELETE /api/v1/users/{id}` removes the user document only. Their tasks remain, still queryable via `GET /api/v1/tasks` and `?user_id=...`. There is no documented policy.
- **Recommendation:** Decide a policy (cascade delete, reject with 409 while tasks exist, or soft delete) and record it as a decision. For a healthcare-oriented project, soft delete with retention is the closest analogue to record-retention requirements.
- **Acceptance Criteria:** A decision recorded in the planning docs, and one atomic API test asserting the chosen behavior.

### [AUDIT-API-05] Unrestricted Cross-User Data Access (Pre-Auth)
- **Severity:** Medium (expected at this stage; tracked so it is not forgotten)
- **Related Tickets:** `[SMP-EP3-TK01-AUTH]`
- **Affected Files:** `src/api/tasks.py` (L72–79), `src/api/users.py` (L59–70, L101–168)
- **Finding:** Any client can list all users, read every user's tasks (omitting `?user_id` returns all tasks), change any user's email or password, and delete any user. This is consistent with the decision to defer authentication (`[Q-SAMPLE-REORG-01]`), but no ticket explicitly lists these endpoints as requiring authorization changes.
- **Recommendation:** Add explicit acceptance criteria to `[SMP-EP3-TK01-AUTH]`:
  - `user_id` derived from the token, not from the body or query.
  - `GET /tasks` without a filter is removed or admin-only.
  - Users may only modify themselves.
- **Acceptance Criteria:** Epoch 3 tickets enumerate each endpoint with its required authorization rule.
- **Devin re-Cognito:** With Cognito, FastAPI validates the JWT and takes the user identity from the `sub` claim. `POST /users`, password updates, and user deletion move to Cognito (`SignUp`, `ChangePassword`, `AdminDeleteUser`). Task queries are always filtered by `sub`, so cross-user reads become impossible by construction.

### [AUDIT-API-06] Input Bounds: `user_id` Format, Pagination, Metadata Size, Password Length
- **Severity:** Low
- **Related Tickets:** `[SMP-EP1-TK02]`, `[SMP-EP1-TK04]`
- **Affected Files:** `src/schemas/task.py` (L17, L20, L28), `src/schemas/user.py` (L20, L28), `src/api/tasks.py` (L72–79), `src/api/users.py` (L64–66)
- **Finding:**
  - `TaskCreate.user_id` accepts any string; format errors surface as a generic 400 from the lookup.
  - List endpoints return entire collections with no `limit`/`skip`.
  - `metadata: dict[str, Any]` has no size or depth limit, and free-form fields are a common path for PHI to enter unexpectedly.
  - PATCH replaces `metadata` entirely rather than merging; this is reasonable but undocumented in OpenAPI.
  - `password` has `min_length=4` and no `max_length`; bcrypt 4.x silently ignores bytes beyond 72, so two different long passwords can verify identically.
- **Recommendation:** Add ObjectId format validation, `limit`/`skip` query params with a sensible cap, a metadata size cap, OpenAPI descriptions of replace semantics, and `max_length=72` (or pre-hash) for passwords.
- **Acceptance Criteria:** One schema test per new constraint; OpenAPI docs describe metadata replace semantics.

### [AUDIT-API-07] `Task.user_id` (str) vs. `User.id` (ObjectId) Type Decision Undocumented
- **Severity:** Low

## D. Tests & Fixtures

### [AUDIT-TEST-01] API Tests Set Up State via POST Instead of Fixtures
- **Severity:** High (directly contradicts `AGENTS.md` §3.1 atomic and layered-fixture rules)
- **Related Tickets:** `[SMP-EP1-TK03]`, `[SMP-EP1-TK04]`, `[TASK-AUDIT-01]`
- **Affected Files:**
  - `tests/api/test_users.py`: L117–129, L136–150, L173–189, L192–203, L206–216, L219–233, L248–261
  - `tests/api/test_tasks.py`: L126–139, L142–162, L169–187, L214–226, L229–244, L247–262, L279–293
- **Finding:** Read, update, and delete API tests create their own data via `client.post(...)` with inline dictionaries, instead of consuming `persisted_user` / `persisted_task`. Each such test therefore also exercises (and depends on) the create endpoint — a create+read or create+update bundle that `AGENTS.md` explicitly forbids. If `POST` breaks, every downstream test fails, obscuring the actual broken operation. Delete tests additionally verify via `GET` (delete+read bundling) instead of checking the database directly.
- **Recommendation:**
  - Read/update/delete API tests consume `persisted_user` / `persisted_task` / `persisted_tasks`.
  - Post-condition checks go directly against the database (`await User.get(id) is None`), not through another endpoint.
  - Create tests consume a raw payload fixture (see `[AUDIT-TEST-02]`).
- **Acceptance Criteria:**
  - No test outside the "CREATE" sections calls `client.post`.
  - No delete test calls `client.get`.

### [AUDIT-TEST-02] Fixture Layering Violations and Missing Raw Payload Fixtures
- **Severity:** Medium
- **Related Tickets:** `[SMP-EP1-TK01]`, `[SMP-EP1-TK04]`
- **Affected Files:** `tests/conftest.py` (L114–126, L131–154), `tests/unit/test_user_model.py` (L134–135), repeated literal `"654321654321654321654321"` in `tests/api/test_users.py` and `tests/api/test_tasks.py`
- **Finding:**
  - `sample_tasks_raw_data` is declared as Layer 1 (pure data), but it depends on `persisted_user`, which performs database inserts. Layer 1 is supposed to have no database side effects.
  - `persisted_user` depends on `persisted_users`, so requesting one user inserts three. This produced the earlier surprise and the hard-coded `assert await User.count() == 2` workaround.
  - There are no raw *API payload* fixtures (plaintext password, `UserCreate`-shaped), so API create tests inline their dictionaries.
  - The nonexistent-ID literal is repeated across files.
- **Recommendation:**
  - Make `sample_tasks_raw_data` pure (omit `user_id`, or take a placeholder), and have `persisted_tasks` attach `persisted_user.id` when inserting.
  - Make `persisted_user` insert only one user (from `sample_users_raw_data[0]`); keep `persisted_users` for multi-user tests.
  - Add `user_create_payload`, `task_create_payload`, and `nonexistent_object_id` fixtures.
  - Replace `count() == 2` with an assertion derived from fixture length, or rely on the single-user fixture.
- **Acceptance Criteria:** No Layer 1 fixture depends on a persisted fixture; no magic ObjectId literals remain in test bodies.

### [AUDIT-TEST-04] Demo-Mode Test Does Not Exercise the Lifespan Hook
